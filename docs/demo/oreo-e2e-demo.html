开场：今天讲什么

1 分钟

大家好。今天这次分享，框架整体我只用三分钟带过，大部分时间放在测试数据上。因为大家日常真正花时间、真正容易出错的地方都在这里：加一个 case 的数据该写在哪、新产品怎么进到用例里、接口改了响应怎么更新、检查报错了怎么看。

今天的内容分三块：数据怎么组织，响应怎么录和怎么改，最后是怎么守住质量，包括一张常见问题排查表。

01

框架一页速览

3 分钟

先用一页把框架过一遍。我们有两个执行层：@api 走 genie-rest，证明业务规则和接口契约；@playwright 走浏览器，证明用户看到什么、能做什么。

每个场景从上到下是这样跑的：Feature 里写业务步骤，Snippet 把步骤组合起来，最底下调 Genie 自带步骤或者我们的 Java glue。请求体、产品、期望响应，全部放在 JSON 测试数据里，Feature 和代码里都不写。这就是为什么今天要重点讲数据：用例的大部分变化，最后都落在数据文件里。

还有一个设计决定要先记住：一个生命周期事件一个 Feature 文件，产品是 Examples 里的行。同一个事件对所有产品流程一样，新上一个产品只是多一行，而不是复制一套用例。

flowchart LR
  F[Feature
业务步骤] --> S[Snippet
步骤组合] --> G[Genie 步骤
+ Java glue] --> X[被测系统]
  D[(测试数据
请求 · 产品 · 录制响应)] --> G
  R[ProductDatFiles
产品注册表] -. sync-examples .-> F
features/{api|ui}/<域>/<事件>.feature↔ data/{api|ui}/<事件>.json↔ data/api/expected/<事件>/<用例ID>.json
02

用例 ID：数据的钥匙

3 分钟

数据这一块，第一个要理解的是用例 ID。它写在场景名最前面的方括号里，它不是给人看的编号，而是取数据的钥匙。

Scenario Outline: [TC-TRADE-EARLY-TERMINATION-<product_type>-API-001] <product_type> trade status is updated to Terminated ...
TC-TRADE-EARLY-TERMINATION → 数据文件 trade_early_termination.json· FX_TRF → 产品· API → data/api/· 001 → 第几个 case

拆开看：事件部分转成小写加下划线，就是数据文件名；产品段决定用哪个产品的数据和 dat 文件；API 或 UI 决定去 data/api 还是 data/ui；最后是编号。

Outline 里写 <product_type>，运行时会被每一行产品替换，所以一行 ID 覆盖所有产品。没有产品段的 ID，比如 TC-TRADE-CREATION-API-004，就是一个不区分产品的 case，一般是负向用例。还有一种按数据集编号的 Outline，ID 末尾写 -API-<case>，每个数据集是一个独立的业务 case。

因为 ID 是钥匙，所以有几条硬规则：它不能写成标签；数据文件名必须和 Feature 文件名一致；层要和 Feature 所在目录一致。这几条离线检查都会查。

坑把 ID 写成 @TC-... 标签是没用的，框架只从场景名里读。要单独跑一个 case，用 --name 按场景名筛选，不要用 --tags。
03

四层合并

4 分钟

拿到 ID 以后，框架去数据文件里把这个 case 的数据合并出来。一共四层，后面的覆盖前面的，每一层都是可选的。

defaults 所有 case 共用→ byProduct[P] 这个产品不同的地方→ case 自己的那一行→ 这一行里的 byProduct[P]

合并规则只有三条：对象按 key 合并，数组和值整体替换，写 null 就删掉这个字段。数组没有"追加"，想改数组里的一个元素，就把整个数组写出来。这样做的好处是，看最后一层就知道发出去的是什么。

最重要的一条习惯：一行数据只为"和默认值不一样"的 case 存在。正向 case 跑默认值就够了，不用写行。大家看这个文件，三个 case，第一个只写了响应里哪些字段每次会变，第二个把 data 清空做负向，第三个连请求都没改。

{
  "defaults": {
    "request": { "eventType": "EarlyTermination", "data": [ ... ], "tradeIds": ["PLACEHOLDER"] }
  },
  "cases": [
    { "id": "TC-TRADE-EARLY-TERMINATION-<product_type>-API-001",
      "dynamicFields": { "msg": "type", "data.results[*].tradeId": "type" } },
    { "id": "TC-TRADE-EARLY-TERMINATION-<product_type>-API-002",
      "request": { "data": [] } },
    { "id": "TC-TRADE-EARLY-TERMINATION-<product_type>-API-003",
      "dynamicFields": { "msg": "regex:.*status 'Dead' does not permit 'EarlyTermination'.*" } }
  ]
}

另外几个常用能力：use 按名字引用 common.json 或本文件 shared 里的数据块（两边同名会报错）。只有一个事件用的块放在它自己的 shared 里，比如 trade-basic、stepin-full 就在 trade_creation.json。每一层的 use 是叠加的，不是覆盖：defaults 用了一个块，某一行再 use 另一个，两个都生效，块先合并，再合并这一层自己写的值；${date:T+2} 是今天往后两个日历日，运行时才填；datFile 选这个产品文件夹里的另一个 dat 文件，做产品变体。basic.productId 永远不用写，步骤会按产品自动填。

写完数据，怎么确认它合并出来是对的？用 case 命令，它会打印这个 case 用了哪几层、最终请求是什么、比对哪个期望文件。

mvn -Ptest-data process-test-classes "-Dexec.args=case TC-TRADE-CREATION-FX_TRF-API-001"
演示跑上面这条命令，指着输出讲：applied layers、dat file、request、dynamicFields、expected file。
坑同一个 case 被两行匹配到会直接报错，比如既写了 -<product_type>-API-002 又写了 -FX_TRF-API-002。产品差异放进那一行的 byProduct，不要再拆一行。另外，拼错的 key（比如 byproduct）会在加载时报错，而不是被悄悄忽略。
04

产品与 sync-examples

5 分钟

接下来讲产品是怎么进到用例里的。这里有三样东西配合。

第一，能力，Capability。每个生命周期事件、fixings、cortex formula、product upload 都是一个能力。第二，Feature 里每个带 <product_type> 的 Outline 打一个 @capability#<名字> 标签，说明它测的是哪个能力。第三，产品注册表 ProductDatFiles，每个产品一个常量，写明它支持哪些能力。

FX_TRF(SUPPORT_CAPABILITY),                                        // 全部能力
FX_NEW(except(SUPPORT_CAPABILITY, ALLOCATION, PORTFOLIO_REASSIGNMENT)), // 缺几项
FX_DCD(CREATE, EARLY_TERMINATION),                                 // 只支持少数几项

有了这三样，Examples 里该有哪些产品就是确定的：支持这个能力的所有产品，按注册表顺序排列。所以 Examples 里的产品行没有人手写，由 sync-examples 生成。

mvn -Ptest-data process-test-classes "-Dexec.args=sync-examples"

它对每个 Outline 打印一行：unchanged 没变化，add X 加了产品，remove Y 去掉了产品，reordered 调了顺序，reformatted 只调了格式。打印完看 git diff，提交。

拿最近的一个真实变化举例：FX_PSCRIPT_TRF 原来不支持 cancellation、allocation、amendment 和 portfolio reassignment，现在改成支持全部能力。跑一次 sync-examples，就会在这几个事件的 Outline 上看到 add FX_PSCRIPT_TRF。这些新增的 case 还没有录制响应，下一节讲怎么录。

sync-examples 有一个很重要的特点：只要任何一个 Feature 文件有问题，它一个字都不写，先把问题全部列出来。它会拒绝这些情况：

它拒绝的情况怎么改
Outline 没有 @capability# 标签，或者有两个每个带 <product_type> 的 Outline 恰好一个
标签名不认识（大小写敏感）用 Capability 里的名字，报错信息会列出所有已知名字
标签打在 Feature 或 Examples 上只打在 Scenario Outline 那一行
Examples 不是单列 product_type产品以外的差异放进数据的 byProduct
产品表里有注释行或空行删掉，行由注册表决定
某个能力没有任何产品支持先在注册表里给产品加上这个能力

想看某一个产品到底会跑哪些 case，不用自己去 grep feature，用 product 命令。它先给一张按能力的表，每个能力在不在注册表、有几个 API 和 UI Outline，最后一列留给 QA 填"支持 / 不支持"；再列出每个 Outline 换成这个产品后的用例 ID、标题、所在文件，以及 Examples 里现在有没有这一行。还没注册的新产品也能跑，会列出全部能力。

mvn -Ptest-data process-test-classes "-Dexec.args=product FX_TRF"

| Capability | Registry | Outlines    | QA: supported? |
| create     | yes      | 4 API, 5 UI |                |
| stepInFull | yes      | 1 API, 1 UI |                |
...
| Capability | Case ID                                  | Title | Feature | Examples |
| create     | TC-TRADE-CREATION-FX_TRF-API-001         | ...   | ...     | row      |
坑想让某个产品暂时不跑某个事件，不要在 Examples 里把那一行注释掉，这会让工具和检查都失败。正确做法是在 ProductDatFiles 里把这个能力从产品上去掉，比如改成 except(SUPPORT_CAPABILITY, CANCELLATION)，再跑一次 sync-examples。

负向用例和权限用例不带 <product_type>，也不打能力标签，sync-examples 不会碰它们。校验规则不随产品变化，用一个代表产品就够了。

05

第一次录制

5 分钟

现在讲响应。每个 API case 结束时，会把整个响应和 data/api/expected/<事件>/<用例ID>.json 做严格比对，多一个字段、少一个字段、值变了，都会失败。

期望文件不是手写的，是录出来的。一个新 case 第一次跑，文件不存在，框架会把真实响应录下来，然后故意失败一次，报错是 Expected response recorded to ...: review it against the requirement, commit it, run again.。这次失败是正常的，它在提醒你：先审查录下来的内容，再提交。

坑录制只说明系统做了什么，不说明它应该做什么。录进去一个错误的值，就等于写了一个错误的期望，之后每次都会"通过"。所以录完一定要对着需求逐个字段看。

那每次运行都会变的值怎么办？比如交易 ID、日期、消息里的任务号。在数据里给它配 dynamicFields 规则，录制时这些位置会被换成占位符，比对时只检查规则要求的东西。

规则还检查什么典型用法
type值存在、类型对；数组只检查是数组交易 ID、日期
type-tree整个结构、数组长度、每个叶子的类型每次内容不同但结构固定的对象
regex:<pattern>值匹配正则消息里带一个变化的编号
var:<name>等于本次运行存下的变量var:createdTradeId，确认查到的就是刚建的那笔
ignore不检查其他规则都不行时才用

路径写法：key 用点连接，[n] 表示数组的某一个元素，[*] 表示所有元素，比如 data.results[*].tradeId；* 单独作为一个 key，表示对象的每一个值，比如 "data.fixings.*": "type"。像 FX:EURSGD@[BFIX]-1500-JP TYO 这种本身带点或方括号的 key 写不进路径，就用 * 匹配。

规则要在录制之前配好，而且要写对：规则的路径在响应里不存在，录制会直接失败，报错结尾是 not recorded。regex 不匹配、var 的值对不上，也一样。所以新产品不要提前猜规则，先录一次，再让工具给建议：

mvn -Ptest-data process-test-classes "-Dexec.args=suggest trade_creation"

suggest 什么都不写，只打印两件事：一是哪些值看起来是生成的，比如 UUID、时间戳、和上一次提交的录制相比变了的值，建议用什么规则、放在哪一层（defaults、byProduct 还是某一行）；二是哪个 case 做基础 case 最省字符。每条建议都要人来判断，比如请求里固定的日期是数据，不是动态值。模式认不出来的，再跑第二次，第二次失败在哪个值上，那个值就是动态的。

负向用例一般写 "dynamicFields": null，清掉继承来的规则，因为错误响应的结构和成功响应不同，继承来的路径在里面根本不存在。

06

更新响应

6 分钟

接口有意改了，比如加了一个字段，比对失败了，怎么办？失败信息里已经写好了下一步：If the change is intended, run again with OREO_EXPECTED=update, compact ...。但先要判断这是哪一种失败：

失败的是…该做什么
一个每次都会变的值不是更新，补一条 dynamicFields 规则，再重录
接口有意的变化用 update 模式重录
不该变的值变了这是 bug，不要重录

确定是有意的变化，就按三步走：

# 1. 重录：只选要更新的 case
OREO_EXPECTED=update mvn -B test -Dtest=OreoTest "-Dcucumber.options=--name ^\[TC-TRADE-CREATION-FX_TRF-API-001\].*$"
#    PowerShell: $env:OREO_EXPECTED = "update" ... 跑完 Remove-Item Env:OREO_EXPECTED

# 2. 压缩
mvn -Ptest-data process-test-classes "-Dexec.args=compact trade_creation"

# 3. 检查，再去掉 update 模式跑一次，必须通过
mvn -Ptest-data process-test-classes
mvn -B test -Dtest=OreoTest "-Dcucumber.options=--name ^\[TC-TRADE-CREATION-FX_TRF-API-001\].*$"
坑update 模式下不做比对：它直接把这次的响应写进文件，然后让用例通过。所以一，筛选条件要窄，选中的每个 case 都会被覆盖；二，跑完一定要把环境变量清掉，否则之后每次运行都在重录、永远是绿的；三，重录完必须看 git diff。

为什么要压缩：基础 case 和 patch

同一个产品的几个变体 case，响应大部分是一样的。所以数据文件里声明一个基础 case，比如每个产品的 -API-001，其他变体的期望文件只存和它的差异，也就是一个 patch。

"defaults": { "expectedBase": "TC-TRADE-CREATION-<product_type>-API-001" }

// TC-TRADE-CREATION-FX_TRF-API-002.json 压缩后
{ "_base": "TC-TRADE-CREATION-FX_TRF-API-001",
  "_patch": [ { "op": "replace", "path": "/data/trade/basic/eventStatus", "value": "..." } ] }

录制总是写完整的响应，compact 再把变体变成 patch。好处是：接口加了一个所有 case 都有的字段，diff 里只有基础文件变了，审查起来一目了然。压缩是安全的：有任何问题它一个文件都不写，跑第二次不会再有变化。

跨事件共享的部分：_shared

还有一层去重：交易的 basic 和 instrument 在创建、查询、审批这些事件的响应里都会出现，而且对同一个产品基本一样。事件在数据里声明 sharedFragments，路径对应一个名字，常用的是 api/common.json 里的块 trade-response-parts。compact 时，这部分每个产品只存一份，放在 expected/_shared/basic/<P>.json 和 instrument/<P>.json，case 文件里只留一个引用，和共享文件不同的 key 就写在引用旁边，比如审批后 version 变成 2。

// api/common.json 里的块 trade-response-parts，事件在 defaults.use 里引用它
"sharedFragments": {
  "data.trade.basic": "basic/<product_type>",
  "data.trade.instrument": "instrument/<product_type>" }

// 压缩后的 case 文件
"data": { "trade": {
  "basic": { "_shared": "basic/FX_TRF", "version": 2 },
  "instrument": { "_shared": "instrument/FX_TRF" } } }

路径不一样的事件，比如 trade_approval_rejection 是 data.basic，少一层 trade，就在自己的 sharedFragments 里写自己的路径，名字用同一个。新产品不需要手动处理 _shared：第一次 compact 会从它的第一个录制 case 生成。

compact <event> 和 compact all 的区别：只压一个事件时，已有的共享文件保持不动；compact all 会重建所有共享文件，每部分取第一个 case，没人引用的共享文件会删掉。"第一个"的顺序是：先 api/common.json 里 sharedSources 列出的事件（现在是 ["trade_creation"]），再按名字排其他事件，事件内按 case ID 排。所以基准永远是 trade creation 录下来的那份，amend、approve 只在引用旁边写自己不同的 key。所以共享文件生成之后才加的规则，要跑 compact all，否则后来才 mask 的值还留在共享文件里，每个 case 都会多一个不同的 key。

坑改基础 case，要连同它的变体一起重录。只重录了 -API-001，变体的 patch 可能对不上新的基础文件，变体会失败，报错里有 The patch does not fit。解决办法也写在报错里：用 update 模式把那个变体也重录一次（update 模式不读旧文件，所以不会被坏 patch 卡住），然后 compact。更省事的做法是一开始就按 -API-\d+ 把整组一起录。

最后一种情况：有些 API case 根本不比对响应，比如调完一串接口去查数据库的审计用例。给它打 @expected#none，就不需要期望文件；检查也不会再要求它有，留着旧文件反而会报错。

07

离线检查

3 分钟

前面讲的所有规则，都由一条命令守着。它不开浏览器、不连环境、一分钟以内，提交数据、Feature 或注册表之前一定要跑。

mvn -Ptest-data process-test-classes

它先跑六个单元测试，保证"合并数据""比对响应"和"给建议"这几段逻辑本身是对的；任何一个失败，后面就不跑了。然后依次做九项检查，每项输出 [ok] 或 [FAIL]，最后一行是 No problem. 或问题总数。

检查项查什么
data files are well formed每个数据文件能加载，没有未知 key，没有重复行
every feature case resolves每个场景的 ID 都能解析，数据能合并出来
every row and event file has a feature没有孤儿数据：每一行、每个文件都有对应的场景
every API case has its expected file每个 API case 都录了；每个期望文件都有对应的 case
the rules agree with the expected filesdynamicFields 规则和录制文件里的占位符一致
the expected files are compacted有没有该压缩没压缩的，按 compact all 算，包括共享文件（只是警告）
every setup name used exists代码里用到的 setup 数据都有文件
the product Outlines' Examples match the registryExamples 和注册表一致，即 sync-examples 不会再改任何东西
every product with a capability has its dat file支持能力的产品都有 dat 文件
坑检查读的是 target/test-classes 里复制过去的数据。如果它和 src 不一致，工具会直接停下，让你重跑命令；如果是删了文件，复制品会一直留在 target 里，要在命令前加 clean。
08

常见问题排查

4 分钟

最后这张表是今天最实用的部分，建议大家收藏。左边是你会看到的现象或报错，中间是原因，右边是怎么做。

看到的现象原因怎么做
新 case 第一次跑失败：Expected response recorded to ...正常，第一次录制审查文件内容、提交、再跑
比对失败，信息里有 Expected file: ...响应和录制不同先判断：动态值 → 加规则；有意变化 → update 重录；否则是 bug
录制失败，结尾是 not recorded规则路径不在响应里，或 regex / var 对不上改规则；负向 case 用 "dynamicFields": null
只改了基础 case，变体失败：The patch does not fit变体的 patch 对不上新的基础文件update 模式重录变体，再 compact

Q&A

1 分钟

总结一下今天的三句话：ID 是数据的钥匙；Examples 由注册表生成；响应是录出来的，但必须审过才算数。我就讲到这里，大家有什么问题？

可能被问到的问题

问：为什么数组不能追加，要整个写？答：追加要在每一层之间推算最终结果，容易出错；整体替换只看最后一层就知道发了什么。代价是偶尔要重复写几个元素。

问：期望文件能不能手改一个值？答：不能。手改的值没有经过真实系统验证，下次重录也会被覆盖。改规则或重录。

问：为什么 update 模式不做比对？答：它的用途就是覆盖旧文件；如果旧文件已经坏了，比如 patch 对不上，再去读它就永远录不进新的。

问：文档里写的 TestDataTool compact 能直接跑吗？答：不能。TestDataTool 只是 Maven 调用的类，命令都是 mvn -Ptest-data process-test-classes "-Dexec.args=..."，exec.args 就是要跑的子命令，不写默认是 check。

问：本地能跑吗？答：离线检查和 case 命令不连测试环境，有公司 Maven 仓库就能跑；真正的用例要在公司环境，因为会连真实系统下单。
