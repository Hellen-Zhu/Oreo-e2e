开场：我们要解决什么

2 分钟

大家好，今天花三十分钟左右，把我们现在的 E2E 框架完整过一遍。我会按"由面到点"的顺序讲：先看全景，再看一个用例是怎么跑起来的，最后落到大家最常做的事，比如新上一个产品、更新一个响应。

先说为什么要重新整理。旧的做法有几个问题：每个产品、每个 case 都要单独写一条数据，产品 ID 和请求引用反复复制；一个产品要支持某个事件，就要复制一整套模板；每个 API case 的期望响应都是手工复制进去的完整 JSON，15 个 case 就有七百多行；而且数据缺了只打一个 warning，测试照样跑。

我们的产品是一个一个上线的。所以这套框架的核心目标只有一句话：新上一个产品，应该是加一行配置，而不是复制一堆用例。后面讲的所有设计，都是围绕这句话展开的。

01

全景：从需求到报告

4 分钟

先看全景。一个需求进来，到最后出测试报告，中间分成三个阶段，每个阶段有一份标准文档。

第一阶段是测试分析：从 Story 的验收标准出发，拆出测试点，决定每个测试点在 API 层测还是 UI 层测、用什么证据证明。这一步不写任何 Gherkin。

第二阶段是生成 Feature：把测试点写成业务语言的场景，决定放在哪个文件、叫什么、编号是多少。

第三阶段是实现：让每一个步骤真的能跑。这里又分几层：Feature 里的业务步骤，由 Snippet 组合出来；Snippet 再调用 Genie 自带的步骤或者我们自己的 Java glue；请求体、产品、期望响应这些数据，全部放在 JSON 测试数据里，不写在 Feature 和代码里。

大家记住一个原则：Feature 只写业务，数据只放在数据文件，代码只做通用能力。三者各管一块，谁也不往对方那里塞东西。

02

两层测试各证明什么

2 分钟

我们有两个执行层。API 层打 @api 标签，走 genie-rest，不开浏览器。业务规则、校验、权限、maker-checker、状态流转、接口契约，都在这一层证明。

UI 层打 @playwright 标签，走 genie-playwright，用 Edge。它只证明用户看到了什么、能做什么：页面上显示的状态、按钮能不能点、表单行为、通知。

选哪一层，规则只有一条：在能拿到证据的最低一层测。API 测试快、稳、维护成本低，所以后端规则不要为了"看得见"搬到 UI 上测。反过来，UI 用例的前置交易可以通过 API 造出来，这不会让它变成 API 用例，因为它的证据在浏览器里。

要证明的是…层
业务规则、校验、权限、maker-checker、状态流转、审计@api
请求 / 响应契约：字段、类型、错误码@api
用户看到的状态、可用的操作、表单、通知@playwright
03

事件是文件，产品是行

4 分钟

这是整个框架最关键的一个设计决定。我们当时讨论过：一个产品一个 Feature 文件，还是一个生命周期事件一个文件？结论是按事件拆文件，产品作为 Examples 的行。

原因很简单。同一个事件，比如提前终止，对所有产品的业务流程是一样的，只是数据不同。如果按产品拆，新上一个产品就要把十几个事件的用例全部复制一遍；按事件拆，新产品只是在每个事件的 Examples 里多一行。

所以现在是：一个事件、一个层，对应一个 Feature 文件，比如 features/api/trading/trade_early_termination.feature；同名还有一个数据文件 data/api/trade_early_termination.json。

大家看这个场景。场景名最前面方括号里的是用例 ID，<product_type> 会被每一行产品替换。这个 ID 不是装饰，它决定了这个用例读哪个数据文件、哪个产品、哪一行数据。还有一个 @capability#earlyTermination 标签，它决定了 Examples 里应该有哪些产品，这个后面讲新产品时再展开。

@ADO#positive @ADO#smoke @capability#earlyTermination
Scenario Outline: [TC-TRADE-EARLY-TERMINATION-<product_type>-API-001] <product_type> trade status is updated to Terminated ...
  Given a live '<product_type>' trade is created via api
  When maker has valid data for EarlyTermination event
  And performs the EarlyTermination event via api
  ...
  Then the trade basic event status is 'Terminated'

  Examples:
    | product_type    |
    | FX_TRF          |
    | FX_PSCRIPT      |
    | FX_PSCRIPT_FSKO |
    | FX_PSCRIPT_TRF  |

用例 ID 拆开看是这样的：

TC-TRADE-CREATION → 事件 trade_creation· FX_TRF → 产品· API → 层· 001 → 第几个 case

另外一点：负向用例和权限用例，比如"数据格式错误被拒绝"，一般只用一个代表产品来写。校验规则不会因为产品而变，每个产品都跑一遍只会增加时间，不会增加覆盖。

屏幕打开 trade_early_termination.feature，指出方括号里的 ID、@capability# 标签和 Examples。
04

一个场景怎么跑起来

3 分钟

现在从面落到点，跟着一个场景走一遍。

第一步，场景开始前，ScenarioLifecycleHooks 从场景名里读出用例 ID，找到对应的数据文件，把这个 case 的数据合并好。合并的规则下一节讲。

第二步，合并好的请求被放进场景上下文，比如 _tc.request，以及展开后的字段 basic.counterpartyName。同时报告里会写出这次用了哪几层数据，出了问题一眼就能看到数据从哪来的。

第三步，各个步骤和 Snippet 从上下文里取数据去调接口或者操作页面。需要前置交易的，用 setup 数据造出来，比如一笔 Live 状态的交易。

最后一步，API 用例结束时会做一次完整响应的严格比对，跟录制好的期望文件比。这一点很重要，下下节专门讲。

sequenceDiagram
  participant H as Hook
  participant D as 测试数据
  participant S as 步骤 / Snippet
  participant X as 被测系统
  participant E as 录制响应
  H->>D: 用例 ID → 事件文件、产品、行
  D-->>H: 合并后的请求
  H->>S: 放进场景上下文
  S->>X: 调接口 / 操作页面
  X-->>S: 响应
  S->>E: 与期望文件严格比对
05

测试数据：四层合并

4 分钟

测试数据是 JSON，一个事件一个文件，API 和 UI 各自独立，互不读取。

每个 case 的数据由四层合并而成，后面的覆盖前面的：先是 defaults，所有 case 共用；然后是 byProduct，某个产品不一样的地方；然后是这个 case 自己的那一行；最后是这一行里的 byProduct。每一层都是可选的。

合并规则也很简单：对象按 key 逐个合并，数组和值整体替换，写 null 就是删掉这个字段。我们最近把"往数组里追加元素"的能力删掉了，因为它带来的复杂度比收益大。现在想改数组里的一个元素，就把整个数组写出来，最终发出去的是什么，看最后一层就知道。

关键是：一行数据只为"和默认值不一样"的 case 存在。正向 case 跑默认值就够了，根本不需要写一行。大家看这个文件，三个 case，只有很少的几行。

{
  "defaults": {
    "request": { "eventType": "EarlyTermination", "data": [ ... ], "tradeIds": ["PLACEHOLDER"] }
  },
  "cases": [
    { "id": "TC-TRADE-EARLY-TERMINATION-<product_type>-API-001",
      "dynamicFields": { "msg": "type", "data.results[*].tradeId": "type" } },
    { "id": "TC-TRADE-EARLY-TERMINATION-<product_type>-API-002",
      "request": { "data": [] } },
    { "id": "TC-TRADE-EARLY-TERMINATION-<product_type>-API-003",
      "dynamicFields": { "msg": "regex:.*status 'Dead' does not permit 'EarlyTermination'.*" } }
  ]
}

还有两个小工具。一个是 use：把几个事件都要用的数据块放在 common.json，按名字引用。另一个是日期：写 ${date:T+2} 就是今天往后两个日历日，运行时才填进去，不用每次手改日期。

演示运行 mvn -Ptest-data process-test-classes "-Dexec.args=case TC-TRADE-CREATION-FX_TRF-API-001"，展示这个 case 用了哪几层、最终请求长什么样、和哪个期望文件比对。
06

录制响应：严格比对

4 分钟

以前 API 用例只断言几个字段，接口多返回了一个字段、某个值悄悄变了，都发现不了。现在每个 API case 结束时，会把整个响应和 data/api/expected/<事件>/<用例ID>.json 严格比对。

期望文件不是手写的，是录出来的。新 case 第一次跑，文件不存在，框架就把真实响应录下来，这次会失败一次；你审一下内容对不对，提交，之后就是严格比对了。

那每次都变的值怎么办，比如交易 ID、日期？在数据里配 dynamicFields 规则。type 只检查类型，regex 按正则匹配，var 要求等于这次运行里存下的变量，比如刚造出来的交易 ID。录制时这些值会被替换成占位符。

规则还检查什么
type值存在、类型对；数组只检查是数组
type-tree整个结构和每个叶子的类型
regex:<pattern>值匹配正则
var:<name>等于本次运行存下的变量
ignore不检查，其他规则都不行时才用

接口有意改了怎么办？用 update 模式重新录：

OREO_EXPECTED=update mvn -B test -Dtest=OreoTest "-Dcucumber.options=--name ^\[TC-TRADE-CREATION-FX_TRF-API-001\].*$"
mvn -Ptest-data process-test-classes "-Dexec.args=compact trade_creation"

第二条命令是压缩：同一个产品的几个变体，响应大部分一样，压缩后变体只存和基础 case 的差异，也就是一个 patch。最后一定要看 git diff，对着需求审：录进去一个错的值，就等于写了一个错的期望。

还有一种情况：有些 API case 调完一串接口后去查数据库，根本不比对响应，比如审计。给它打上 @expected#none 标签，就不需要期望文件了。

07

UI 的分层

3 分钟

UI 这边分四层，从上到下越来越具体。

最上面是场景，纯业务语言，不出现"点击""输入"这些词，也不出现页面名。下面是 flow snippet，一个业务动作，比如"对这笔交易做提前终止"。flow 不直接碰元素，它调用 page 或 component snippet，这一层才做具体的点击、输入、断言。最底下是元素库，一个 JSON 文件，按名字登记定位方式，优先用 testId。

场景：业务语言→ flow snippet：业务动作→ page / component snippet：原子操作→ 元素库：定位 
@When "^perform the Early Termination event on the '([^']*)' trade$"
    When opens lifecycle action 'early termination' for current trade
    And component dynamic action types amount from stored variable 'earlyTermination.amount'
    And submits lifecycle event and waits for page ready

@Then "^the trade is closed as Terminated$"
    Then the trade has status 'DEAD' and event status 'Terminated' in the blotter

这么分的好处是：页面改版，定位变了，只改元素库；交互方式变了，只改 page snippet；业务场景一行不用动。

新加一个步骤时按这个顺序找：先看有没有现成的 snippet，再看 Genie 自带步骤，再看已有的 Java glue，都没有才写新 Java。几条红线：Feature 里不写接口和选择器，Java 里不硬编码选择器，不加 Thread.sleep。

08

新上一个产品

3 分钟

回到开场那句话：新上一个产品，应该是加一行配置。现在看它是怎么做到的。

产品注册表是 ProductDatFiles，每个产品一个常量，写明它支持哪些能力。能力对应 Feature 里的 @capability# 标签。支持全部能力的，写 SUPPORT_CAPABILITY；缺几项的，写 except(SUPPORT_CAPABILITY, …)；只支持少数几项的，直接逐个列出来。

FX_TRF(SUPPORT_CAPABILITY),
FX_PSCRIPT_TRF(SUPPORT_CAPABILITY);

// 缺几项时
FX_NEW(except(SUPPORT_CAPABILITY, ALLOCATION, PORTFOLIO_REASSIGNMENT)),
// 只支持少数几项时
FX_DCD(CREATE, EARLY_TERMINATION),

然后跑一条命令 sync-examples，工具会把这个产品写进所有带对应能力标签的 Outline 的 Examples 里。Examples 里的产品行没有人手改，都是工具按注册表写的，手改的话检查会直接报错。

所以新上一个产品的完整步骤是：

步骤做什么
1 · 问清楚产品 ID、支持哪些能力、默认 dat 文件、哪些值和默认不同
2 · 注册ProductDatFiles 加一个常量，加 data/dat/<P>/<P>.dat
3 · 写行sync-examples 写入所有相关 Outline
4 · 差异只有和默认值不同的地方才写 byProduct
5 · 录制只跑这个产品的 API case，录制、审查、压缩、提交

这一套流程已经写成了 Claude 的 skill，叫 onboarding-e2e-product，它会先问齐这些信息，缺了就不动手。

演示打开 ProductDatFiles.java 和 Capability.java；运行 sync-examples，展示它打印的每个 Outline 的 add <P> 或 unchanged。
09

怎么跑、怎么检查

2 分钟

运行入口是 OreoTest。有三点大家一定要知道。

第一，mvn test 不是全量。runner 里固定了标签 not @wip 和 @ADO#trade_creation，命令行的筛选是和它叠加的。所以跑出来零个用例，不代表通过，先去看 runner。

第二，筛选用 -Dcucumber.options，不要用 -Dcucumber.filter.tags。我们的 Cucumber 版本不支持后者，它可能被悄悄忽略，结果跑了全部用例。

第三，每次跑 API 都会在真实环境里下单。所以永远先想清楚筛选条件，只跑需要的。

# 按标签
mvn -B test -Dtest=OreoTest "-Dcucumber.options=--tags @api --tags @ADO#smoke"
# 按用例 ID（它在场景名里，不是标签）
mvn -B test -Dtest=OreoTest "-Dcucumber.options=--name ^\[TC-TRADE-CREATION-FX_TRF-API-001\].*$"
# 离线检查：不开浏览器，不连环境
mvn -Ptest-data process-test-classes

最后这条离线检查，提交数据、Feature 或注册表之前一定要跑。它先跑五个单元测试，保证数据合并和比对的逻辑本身是对的；然后检查每个数据文件能加载、每个 case 都能解析、期望文件和规则一致、Examples 和注册表一致。一分钟以内，不需要环境。

另外，runner 是按 Feature 并行的，同时跑三个。所以每个场景要自己准备数据，不能依赖别的场景先跑，也不能共用会被别人改掉的交易或设置。

10

标准与 AI 协作

2 分钟

这套框架的规则都写成了文档，不靠口口相传，而且 AI 也能直接按它工作。

三份标准对应前面说的三个阶段：测试分析、生成 Feature、实现。仓库根目录的 CLAUDE.md 是给 AI 和新同学的工作规则，最前面列了最容易踩的坑，比如 mvn test 不是全量。docs/test-data.md 是测试数据的完整参考。还有两个 skill：一个是新上产品，一个是维护测试数据。

实际效果是：给 AI 一个 Story，它能按标准拆测试点、生成 Feature、复用已有步骤；新上产品时，它会先把该问的问题问齐。我们审它的产出，而不是从零写。

文档什么时候看
CLAUDE.md改任何东西之前
test-layering-standards.md拿到 Story，拆测试点、选层
bdd-feature-generation-standards.md写 Feature
bdd-feature-implementation-standards.md写步骤、snippet、glue、数据

11

现状、下一步、Q&A

2 分钟

最后说一下现状。框架本身已经定型：事件按文件、产品按行、数据分层、响应录制、离线检查，都已经可以用。

还没完成的是数据迁移。API 这边，创建、提前终止、分配、参考数据同步、风险指标这几个事件已经有数据文件；UI 这边是创建、提前终止、novation remaining。其他事件的 Feature 已经在了，但数据文件还没写，所以还有一批 API case 没有录制响应。另外 cancellation 和 amendment 的 setup 数据还没有。

还有一件最近的事：FX_PSCRIPT_TRF 现在支持全部能力了，需要跑一次 sync-examples，再把它新增的那几个 case 录制一遍。

下一步我想请大家一起推进：按事件分工，把剩下的数据文件补上，每补一个事件就录制、审查、提交。流程都在文档和 skill 里，有问题随时找我。

我就讲到这里，大家有什么问题？

可能被问到的问题

问：为什么不按产品拆 Feature？答：同一事件的流程对所有产品一样，按产品拆就要为每个新产品复制所有事件的用例；按事件拆，新产品只多一行。

问：录制的响应会不会把 bug 也录进去？答：会，所以录完必须对着需求审 diff，录制只说明系统做了什么，不说明它应该做什么。

问：每个产品都跑负向用例吗？答：不跑，校验规则不随产品变化，用一个代表产品就够了。

问：本地能跑吗？答：离线检查哪里都能跑；真正的用例要在公司环境，因为会连真实系统下单。
