第 1 讲 · 整体结构

我们测什么，为什么要自动化

被测系统

OREO FX 交易管理门户。覆盖 trade 的整个生命周期：创建、审批、修改、取消、提前终止、分配、fixing 等。

要解决的问题

产品一个个上线，每个产品都要覆盖所有 lifecycle event。产品数 × 事件数，靠手工回归跟不上。

核心设计：事件是文件，产品是行。一个 lifecycle event 对应一个 feature；上线一个新产品，只是在 Examples 里多一行，就能复用所有 event 的 case。

这一页讲清楚“为什么这样设计”。理解了“产品是行”，后面看到 Examples 不能手改、要用 sync-examples 生成，她就知道原因了。

第 1 讲 · 整体结构

API 和 UI 各测什么

@api

测业务规则

字段校验、状态流转、审批、返回结果。又快又稳，是覆盖的主力。

@playwright

测用户能否完成操作

页面流程、提示信息、blotter 展示。只验证关键路径。

UI 的前置条件通过 API 准备：比如 a Live '<product_type>' trade exists in the blotter。它不登录、不导航，trade ID 存在 createdTradeId。UI scenario 不能直接调用 API snippet。

分层的依据在 docs/standards/test-layering-standards.md。一个验收标准先问：这是业务规则还是用户操作？

第 1 讲 · 整体结构

改动放在哪：先复用，最后才写 Java

1

已有的 flow、page、component 或 API snippet 能表达 → 直接复用

2

Genie 内置 step 能做到 → 在 snippet 里使用

3

已有的 glue（glue/api、glue/ui）能做到 → 在 snippet 里调用

4

用上面这些组合出一个新 snippet

5

都做不到 → 才写新的 Java，一次只加一个能力

这是 CLAUDE.md 第 3 节的规则，按顺序往下找，遇到第一个合适的就停。老代码里有一些 wrapper、sleep，不要模仿，也不要顺手重构。

第 2 讲 · Genie 运行机制

Genie 是什么

公司内部基于 Cucumber-JVM 和 JUnit 封装的测试框架。它把 REST、数据库、Playwright、报告和并行做成模块，项目只需要写业务步骤。

OreoModule（我们的模块）

注册 glue：Java 包 com.example.module.oreo.glue 和 classpath:snippet

Spring

Rest

Jdbc

Sql

Database

依赖的模块按顺序加载，各自带来内置 step

写新步骤之前，先查内置 step 目录：docs/genie_rest_glue_catalog.md 和 docs/genie_playwright_glue_catalog.md。

打个比方：Cucumber 是发动机，Genie 是整辆车，oreo-e2e 是装在车上的货。打开 OreoModule.java，看 getDependencies 和 getGluePaths 两个方法。

第 2 讲 · Genie 运行机制

入口：OreoTest 的三个注解

注解作用要记住
@RunWith(Genie.class)由 Genie 接管 JUnit 的运行mvn test -Dtest=OreoTest 跑的就是 Genie
@CucumberOptionsfeature 在哪、glue 在哪、默认 tagglue 有两个来源：Java 包和 snippet
@GenieOptions环境配置文件、并行方式qa.properties，FEATURE 模式，3 个并发

固定 tag：not @wip 和 @ADO#trade_creation，命令行的 filter 会和它们叠加。所以 mvn test 不等于全量；跑出 0 个 case 时，先查 tag。选 case 只用 -Dcucumber.options，不用 -Dcucumber.filter.*。

打开 src/test/java/com/example/module/oreo/OreoTest.java 对照讲。SeedTest 是另一个入口，用来给 UAT 批量下 SIT seed，不是测试，mvn test 不会跑它。

第 2 讲 · Genie 运行机制

Snippet：用文本写的 step 定义

# snippet/api/common_api.snippet
@Given "^start a new api request as user '([^']*)'$"
    Given start building a new request
    And set the user header for '$1'
    And set a new request id header

第一行是正则

$1 是正则捕获的参数，比如 maker、checker

下面是展开的步骤

可以是内置 step、其他 snippet 或 Java glue，一层层展开

所以 feature 可以写成纯业务语言，技术细节全部沉到 snippet 和 glue 里。

这一页是第二讲的重点。现场演示：从 feature 里的一行 step 开始，跳到 snippet，一层层展开，最后落到一个内置 step 或 Java 方法。

第 2 讲 · Genie 运行机制

一个 scenario 的生命周期

启动与筛选

读 properties，加载模块，按 tag 和 name 过滤

@Before

ScenarioLifecycleHooks 等准备工作

执行 steps

逐个匹配 snippet 或 Java glue

@After

失败截图，保存 Playwright trace

报告

每个 scenario 的结果

scenario 之间不共享状态

每个 scenario 都会创建新的 glue 实例

step 之间靠 stored variable 传值

比如 from stored variable 'createdTradeId'

hooks 在 glue/hooks/。trace 的保留方式由 genie.properties 里的 oreo.playwright.trace.mode=RETAIN_ON_FAILURE 控制。

第 2 讲 · Genie 运行机制

配置与环境

genie.properties

公共默认值

Edge 浏览器、headless、超时、trace 模式、risk engine 用 MOCK、元素文件路径

<env>.properties

各环境的地址和账号

dev、sit、qa、uat、pt；默认 qa，由 @GenieOptions 指定

# 切换环境
-Dgenie.properties=./src/test/resources/<env>.properties

地址和账号只能放在 properties 里，不能写进代码、feature，也不能提交。账号按角色通过 config/TestUser 获取。

可以打开 genie.properties 看一下有哪些配置项，但不要在屏幕上展示真实的地址和账号。

第 2 讲 · Genie 运行机制

并行：多进程，不是多线程

master 进程

加载 feature，按 FEATURE 模式切成工作单元，排队

子 JVM 1：串行跑一个 feature

子 JVM 2：串行跑一个 feature

子 JVM 3：一个结束，马上补下一个

为什么

Cucumber-JVM 不是线程安全的

DISCRETE 目录

每个子进程有独立临时目录，读文件必须走 classpath

对 case 的要求

不依赖其他 feature 会改的数据，比如固定的 trade 或用户设置

细节见 docs/genie-parallel-execution.md 第 1 节。并发数不是越高越快：每个子进程都是完整的 JVM，UI case 还有自己的浏览器。

第 3 讲 · 测试数据

录制、同步与离线检查

场景怎么做
新 case 第一次跑没有录制时，会把响应写进 src 并失败一次；检查后再跑
看一个 case 发什么TestDataTool 的 case <ID>
每次都变的字段写 dynamicFields 规则做 mask，再 compact <event>
新产品或新 capability在 ProductDatFiles 注册，再用 sync-examples 生成 Examples
提交之前mvn -Ptest-data process-test-classes（单元测试 + check）

录制展示的是系统做了什么，不是系统应该做什么。录下来的响应和需求对不上时，先停下来问，不要直接接受。

期望文件和 Examples 都不能手改。每次提交前看一遍 git diff，确认没有真实 trade ID、地址或账号。

第 4 讲 · AI 工作流

两条流水线，每一步都有人审批

/writebddfeatures · bdd-agent

story → feature 文件

1. 拆成测试点，决定放 API 还是 UI（qa-layer-test-design）
2. 审批
3. 写成业务语言的 Gherkin（qa-bdd-feature-authoring）
4. 审批

/codetestcases · test-agent

feature → 能跑的 case

1. 补齐数据、snippet、glue（qa-api-test-authoring、qa-e2e-test-authoring）
2. 离线检查和 dry run（qa-bdd-test-execution）
3. 审批后用最窄的 filter 真实运行

跑出来的产品缺陷用 qa-defect-reporting 起草 ADO Bug，确认之后才创建。

这一讲配合 docs/demo/oreo-ai-workflow.html，里面有交接物、失败分流和一个完整的例子。强调 AI 生成的内容同样要经过人审批和 code review。

收尾 · 一定要记住

五条红线

  1. API 运行会下真实的 trade，只能用最窄的 filter
  2. mvn test 不是全量：有固定 tag，选 case 用 -Dcucumber.options
  3. Examples 和期望响应不能手改：用 sync-examples，录制后 compact
  4. feature 里不出现 endpoint、请求体和选择器
  5. 不提交账号、密码、环境地址和真实 trade ID
其余规则让她自己读 CLAUDE.md 第 4 节 Hard stops。这五条是新人最容易出事的地方。

收尾 · 排查

出问题时，先查哪一层

现象先查
step undefinedsnippet 的正则是否匹配，glue 路径是否正确
跑了 0 个 casefilter 和固定 tag 叠加后是否为空
单独能过，并行时失败是否有共享状态，或者用了相对路径
连不上，或者返回 401用的是哪个 properties，账号对不对
和期望响应对不上动态字段没有 mask，还是系统行为真的变了
最后一行最需要判断力：如果是行为变了，要对照需求，确认是缺陷还是需求变更，不能直接重新录制。
