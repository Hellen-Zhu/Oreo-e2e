TASKStory 下面具体的活
用 Related 链接挂到 Feature，不当子项：Test PlanBug仓库 / 文档
  • 不要按产品建 Feature。在仓库里，一个产品只是每个事件 Examples 里的一行。接入新产品用一个可复用的 User Story 模板（见下面"接入产品"），每上一个产品复制一份，工作项和代码的结构就是对应的。
  • Test Plan 按标签分 suite。用例已经打了 @ADO#<suite>、@ADO#positive / negative、@ADO#smoke / regression。Test Plan 按同样的方式分 suite，Feature 里的覆盖数字和 Test Plan 就能对上。
  • 验收标准写成能核对的矩阵。"每个事件 × 每个产品 × 每一层都有用例"能逐项检查，"提高覆盖率"检查不了。

Title
OREO FX — E2E Test Automation (API + UI) for <to fill: Release/PI>
Tags
QA; E2E; Automation
Description

Goal

Prove the OREO FX trade management portal end to end before each release: every in-scope trade lifecycle event, for every live product, at the API layer (business rules) and on the critical UI paths. Provide UAT with ready-to-use SIT trades.

Scope: in

  • Trade lifecycle (API + UI): creation (incl. step-in full/partial), creation approval, amendment and its approval, cancellation and its approval, early termination, partial termination, allocation, fixings, novation (remaining party, full and partial), portfolio reassignment, step-out full/partial, trade query, audit trail.
  • Supporting areas: trade blotter (API + UI), risk metrics retrieval, reference data (currency, marketer, portfolio, product IDs, reasons), refdata sync, Cortex formula management, product compose and schema upload (UI), WebSocket notifications, user preferences.
  • Products: 19 compositions registered in E2E (see the attached coverage matrix). New products are onboarded one at a time with the "Onboard product <X> to E2E" story.
  • SIT seed for UAT: bulk booking of live trades and lifecycle events, with a report for UAT.

Scope: out

  • <to fill: e.g. performance testing, downstream systems beyond OREO's own API>

Approach

  • Layering: @api cases carry most of the coverage (validation, state transitions, approvals, responses); @playwright cases cover what a user must be able to do. UI preconditions are provisioned through the API.
  • Products are rows: each lifecycle event is one feature file, and a new product adds one Examples row to every event it supports.
  • Expected API responses are recorded with dynamic values masked; an offline test data check runs before any environment run.
  • Parallel execution (3 feature files at a time, in separate JVMs). Environments: dev, SIT, QA, UAT, PT.
  • Defects found by a run are raised as ADO Bugs and linked to this Feature.

Open items / risks

  • Async downstream booking: test strategy drafted (live trade pool, downstream stub); waiting on Dev for the final behavior.

公开副本的参考值（不要直接粘贴，换成公司的输出）：46 个 feature 文件；253 条可执行用例（API 147 / UI 106）；127 个 scenario 定义，其中 96 positive / 31 negative，62 smoke / 68 regression；SIT seed 60 个 case（38 笔新交易覆盖 18 个 Itradeable Type，10 类事件共 20 笔，2 笔 step-in）。

Acceptance Criteria
  1. Every in-scope lifecycle event has at least one positive API case for each in-scope product, plus negative cases for its validation rules.
  2. Each critical user journey (create, approve, each lifecycle event's happy path) has a UI case per in-scope product.
  3. The offline test data check passes, with no case left @wip in the release scope unless listed here with a reason.
  4. The full regression on QA passes, or every failure is triaged and linked to an ADO Bug; new cases pass twice in a row.
  5. The SIT seed is booked for UAT, failed bookings are re-run, and the seed report is handed to UAT.
  6. The coverage matrix (event × product × layer) and the run report are attached to this Feature.

接入产品 · 可复用模板 · English

"接入产品 X" User Story

每上线一个产品复制一份，把 <X> 换成它的 composition。验收标准就是仓库里接入一个产品的固定步骤。

Title
Onboard product <X> to OREO E2E
Description

As the QA team, we want product <X> (composition <C>, product ID <P>) covered by the OREO E2E regression, so that every lifecycle event it supports is proven at the API layer and on the critical UI paths before it goes live.

Inputs needed: the product's dat file, its product ID, and the lifecycle events it supports (confirmed by the product owner).

Acceptance Criteria
  1. The dat file and product ID are provided, and the composition is registered in ProductDatFiles.
  2. Its supported capabilities are confirmed; sync-examples writes its Examples rows (no row edited by hand).
  3. The offline test data check (mvn -Ptest-data process-test-classes) passes with no new problem.
  4. New recorded responses are reviewed against the requirement, dynamic values masked, expected files compacted.
  5. The new rows pass twice in a row on QA.
  6. If UAT needs it: a seed row for the product in the SIT seed catalog.
