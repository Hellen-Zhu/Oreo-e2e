OREO QA 智能体流水线

从一个 user story 到能在公司环境跑通的 case：两个 command 负责编排和让你审批，两个 agent 负责干活，五个 skill 规定具体步骤，规则本身只写在 CLAUDE.md 和 docs/standards/ 里。

总体结构：四层，各管一件事

改版最核心的一点是职责分层。公司版把同一条规则抄进好几个 skill，抄着抄着就不一致了；这里每条规则只有一个出处，skill 只写"按什么顺序做、读哪份标准、交出什么"。

Command.claude/commands/

编排顺序、审批关口、写最终文件、保存进度。你直接用 /writebddfeatures、/codetestcases 调用。

Agent.claude/agents/

拿到一份干净的上下文，选对 skill 去执行，把结果原样交回。bdd-agent 做设计，test-agent 做实现和校验。

Skill.claude/skills/qa-*

具体步骤、允许读哪些文件、输出格式（交接合同）。每个 skill 开头写明"规则在哪份标准里，先读完"。

StandardCLAUDE.md · docs/standards/

规则本身：分层、命名、标签、case ID、测试数据、录制、硬性禁止项。改规则只改这里。

command 调 agent 时只传结构化字段（phase、artifactPath、caseIds、where），不附加额外说明。多加的文字会和 skill 自己的指令抢优先级。这是公司版里最好的一条约定，保留了下来。

两条流水线

第一条把 story 变成 feature 文件，全程不需要 Maven，在这台电脑上就能跑完。第二条把 feature 变成能运行的 case，真实运行只能在公司电脑上。

审批 三个关口都由 command 发出，你回复 approve / revise / stop（或 yes / no / edit first）后才继续。

/writebddfeatures：story → feature 文件

输入是 story 文本或文件路径。这个仓库没有接 ADO，只给一个 ID 时会请你把 story 贴进来。

  1. 1
    加载

    确定 storyId；若 .ai-sdlc/<storyId>/state.json 显示已经写过 feature，先问要不要重来。

  2. 2
    阶段 1：测试分层

    调 bdd-agent（phase 1）→ skill qa-layer-test-design。产出测试点表和 JSON 产物 test-layer-analysis.json：每个 TP 一个层（@api 或 @playwright）、一组标签、产品范围、证据强度、风险。组件级的东西列为"交给 FE 仓库"，不在这里造 UI 用例。

  3. 关口
    审批 1 approve / revise / stop

    revise 时只改你说的部分，其他 TP 编号和字段保持不变。

  4. 3
    阶段 2：写 feature 内容

    调 bdd-agent（phase 2）→ skill qa-bdd-feature-authoring。决定文件名和路径（已有的命名优先）、create 还是 append、续编 case ID、生成步骤索引并优先复用现有步骤；所有产品共享的行为写成带 @capability# 的 Outline，Examples 只留表头。

  5. 关口
    审批 2 approve / revise / stop

    你看到的就是将要写进文件的 Gherkin，外加命名依据、TP→场景映射、AC 覆盖、新步骤清单、缺口。

  6. 4
    写文件

    command 自己写，只按审批过的内容；append 前再 grep 一次确认 case ID 没被占用。

  7. 5
    检查

    公司电脑：sync-examples 填产品行，再跑 mvn -Ptest-data process-test-classes。新 API case 报 no expected file 是预期的，录制在下一条流水线里做。其他电脑：给出命令。

  8. 6
    保存进度并总结

    写 state.json（featureFiles、caseIds），下一步提示 /codetestcases <storyId>。不提交。

/codetestcases：feature → 能跑的 case

输入是 storyId（读 state.json）或 feature 路径；没指定 case 时，取工作区里新加的 [TC-...] 场景。只实现、只运行这些 case，不碰整个文件。

  1. 1
    判断在哪台机器

    qa.properties 存在且 mvn -v 成功 → company，可以运行；否则 offline，所有 Maven 步骤改为给出命令。

  2. 2
    实现 + 校验

    调 test-agent：按路径分给 qa-api-test-authoring 或 qa-e2e-test-authoring（先 API 后 UI），然后用 qa-bdd-test-execution 做 check 和 dry-run --strict，失败就在预算内（3 次）修。最后交回 VALIDATION_HANDOFF。

  3. 关口
    审批 3：真实运行 yes / no / edit first

    展示确切的命令和会选中的 case，并提醒：会在 qa.properties 的环境里真实下单；新 API case 第一次运行会录制并失败一次。

  4. 4
    运行与录制

    第一次录制，第二次比对；两次之间变化的值加 dynamicFields 规则后再录一次（record 模式也要先问你）。每份新录制都和需求逐项对照给你看，然后 compact 和离线 check。连续两次通过才算完成。

  5. 5
    失败分流

    按四类处理（见下文）。总共最多 3 轮修复。

  6. 6
    保存进度并总结

    按类别列出改动的文件、每个 case 的结果、重跑命令和待办。不提交。

两个 agent

bdd-agent

资深 BDD 测试工程师。只看 command 传来的 phase 决定做什么，不从对话里猜。

做
阶段 1 调 qa-layer-test-design，写分析产物；阶段 2 调 qa-bdd-feature-authoring。
不做
不写 .feature，不提交，不更新任何跟踪系统；缺的信息写成缺口，不当事实。
修订
只改要求的部分，返回完整结果而不是 diff。

test-agent

资深 QA 自动化工程师。让 feature 可执行，并在不碰环境的前提下证明它准备好了。

做
按路径路由到 API / E2E authoring skill；整批做一次 check + dry run；只修 automation 类失败。
不做
不改 feature 业务措辞、录制文件、Examples 行、产品注册表；从不做真实运行或录制。
交回
各 authoring 报告、校验报告、VALIDATION_HANDOFF。

qa-api-test-authoring

规则
实现标准 §1–§5、§7，docs/test-data.md
做
先给每个步骤定实现方式（REUSE → NEW_SNIPPET → NEW_STEP），再写 case 数据行、API snippet，最后才写 Java
数据

交出

qa-e2e-test-authoring

规则
flow → page / component 分层；元素仓库；Playwright 内置步骤目录
做
新元素先在真实页面上确认（公司电脑），看不到就记为待办，绝不猜选择器；等待只用语义条件
交出
authoring 报告（含看过哪个页面状态）

qa-bdd-test-execution

模式
check · dry-run --strict · real-run · record
选择
能用 case ID 就不用 feature，能用 feature 就不跑全量；Tests run: 0 报为"没选中"，不算通过
交出
每个 case 的结果和失败类别
为什么 dry run 要加 --strict：Cucumber 4 默认把未定义的步骤记为 skipped，dry run 会显示通过。加上后未定义步骤直接失败，这正是 dry run 要抓的问题。

失败怎么分流

公司版的修复循环会"修好"任何失败，包括系统行为和需求不一致的情况，测试被改成迁就缺陷。现在每个失败先分类，只有第一类由 agent 自动修。

类别信号处理
automation未定义步骤、元素找不到或不唯一、缺数据行或 setup、check 报错、编译错误test-agent 修复，再跑这些 case
recordingno expected file、新 case 的第一次比对、两次运行间变化的值录制流程：加 dynamicFields 规则、重录、compact、你复核
behavior状态或业务值和需求不符停下，并列需求与实际；由你判断是缺陷还是需求问题。绝不改数据、录制或步骤去迁就
environment登录失败、连不上、多个无关 case 同时 5xx 或超时停下报告，仓库里没有可修的

走一遍例子

假设 story："提前终止只能对 Live 状态的交易发起，对 Dead 交易应被拒绝"。

  1. 阶段 1
    两个测试点

    TP-001 Live 交易可提前终止：@api，所有支持的产品（capability earlyTermination），证据为回读交易状态（强度 2），smoke。
    TP-002 Dead 交易被拒绝：@api，一个代表产品，证据为拒绝响应（强度 1），regression。不需要 UI 测试点：用户在界面上看不到额外结果。

  2. 阶段 2
    追加到现有文件

    trade_early_termination.feature 已存在 → append。TP-001 已被现有 Outline 覆盖则报告；TP-002 续编为 [TC-TRADE-EARLY-TERMINATION-FX_TRF-API-004]，步骤全部来自索引：a dead 'FX_TRF' trade is created via api → performs the EarlyTermination event via api → failed to '...' '...'。

  3. 实现
    只加一行数据

    步骤都是 REUSE，数据跑 defaults 即可；负向 case 加一行 "dynamicFields": null。check 只报这个新 case 缺录制文件，dry run 通过。

  4. 运行
    录制并复核

    你同意后运行：第一次录下拒绝响应并失败，第二次通过；你确认拒绝信息里说的确实是"交易不是 Live"，compact 后完成。

和公司版的差异

方面公司 ai-toolingoreo-e2e 版本
测试数据YAML，每个 @TC- 一个 key，响应写死在文件里，用 json-unit 占位分层 JSON（defaults → byProduct → 行），响应真实录制，用 dynamicFields 规则屏蔽动态值
Case ID 和标签@TC-... 标签；@smoke、@positivecase ID 写在场景名里；@ADO#smoke、@ADO#positive、@capability#
产品没有产品概念产品是 Outline 的行，由 sync-examples 按注册表写入
层次API、UI 组件、UI 集成、E2E 四层只有 @api、@playwright；组件级列给 FE 仓库
校验mvn clean test --dry-run先离线 check，再 --dry-run --strict；空运行不算通过
真实运行校验后直接跑先审批；新录制逐份对照需求复核
修复失败一律修分四类，行为不符时停下
步骤索引脚本遇到第一个没有步骤的文件就退出；漏掉 @And；需要 bash 4重写：每次生成到 target/ai/，含 @And 和 Java glue，Mac / Git Bash 都能跑
外部依赖ado-agent、debug-agent、/codeuserstorystory 用文本或文件输入，进度存在本地 .ai-sdlc/
